# 天玑 810 真机运行 iOS 16 —— 可行性判定与移植实施方案

> 目标机：OPPO PGCM10 / OPD2A0（项目代号 210A0，产品名 ossi），MT6833（天玑 810）
> 目标系统：iOS 16（iPhone10,3 / D22AP 的 iOS 16.5 20F66 IPSW）
> 文档状态：基于 2026-11-08 在本机上的实测 + 公开资料核实
> 工作区：~/Desktop/iOS16.5_4.1

---

## 0. 先说结论（五条，每条都带证据）

**1）用 Apple 原版引导链（iBoot）在这台机器上启动 iOS：不可能。**
我从你的 IPSW 里实测：iBoot / LLB / SEP 固件全部带 KBAG（加密），iBoot 描述串 iBoot-8422.120.66，载荷 1,110,800 字节、首字节高熵。解密需要 SoC 内的 GID 熔丝密钥，只有 A11 真机的 BootROM 能当解密 oracle。更关键的是 iBoot 按固定物理地址写死访问 AIC / PMGR / SPMI PMIC / ANS2 / AOP——MT6833 上一个都没有。

**2）"真机运行 iOS"在 2026 年已经成立，但走的是另一条路：Apple 开源的 XNU + 从 IPSW 里提取的 iOS 用户态 + 自写平台层 + 关闭安全模型。**
两个先例已经跑到桌面：
- **hakios-mt6768**（Infinix Hot 20，**联发科 Helio G85 / MT6768，Mali-G52**）：iOS **16.5** 用户态 → launchd → backboardd → SpringBoard → 应用，触摸/按键/显示/Mali+Metal/Wi-Fi 全部工作。
- **ios-sweet**（Redmi Note 10 Pro，SM7150）：iOS 16.7.16 用户态到 SpringBoard 首屏，触摸+按键+锁屏+控制中心可用，纯 CPU 渲染 20–30 fps。

**但没有任何 MT6833 的移植**，所以这不是"照抄一下"的活。

**3）你这台机器上已经有一份 iOS 16.5 的系统镜像了 —— 在 xnusys 分区里。**
我实测：`/dev/block/by-name/xnusys` 4,378,820,608 字节，块 0 偏移 0x20 是 `NXSB`（APFS 容器超级块），块 2392 是 `APSB`（APFS 卷超级块），卷名 `System`，字符串里有 `mkapfs.py (darwin-redwood)`、`/redwood/lib/HakiosAudio.driver`、`D22AP-Info.plist`、`16.5`；已用块 0x92f5a×4096 ≈ 2.46 GiB。**这是 HakiOS 工具链生成的 iOS 系统镜像，已经在盘上了。**
→ 也就是说：**rootfs 这一关你不用再做了，缺的是 loader 和 XNU 的 MT6833 平台驱动。**

**4）`fastboot boot` 在这台机器上不可用 —— 我试过了，会把 LK 搞崩。**
实测：`fastboot boot backup/boot.img`（原厂 header v2 镜像，32 MB）→ `Booting  FAILED (usb_read failed with status e00002ed)`，机器复位后 `ro.boot.bootreason = lk_crash`。原厂镜像都能崩，说明 OPPO 的 LK 里 `cmd_boot` 路径是坏的/被裁掉的。
→ **所有实验必须走 `fastboot flash boot`，风险从"零"变成"有"，回滚包已经给你备好了。**

**5）显示是整条路上最省事的一环 —— 不需要写面板驱动。**
LK 会把面板点亮并持续扫描一个 framebuffer，位置在 `reserved-memory/mblock-18-framebuffer`：**物理地址 0x76720000，大小 0x27E0000（≈41.8 MB，4 个 1088×2400×4 缓冲）**，属性 `compatible = "mediatek,framebuffer"`，**没有 `no-map`**（这点很重要，见第 6 节坑 2）。往这块内存里写像素，屏幕就会变——Linux 的 `simple-framebuffer` 和 XNU 的 `sweetfb` 都是这么干的。

**工作量：6–12 个月 · 1–3 人。最短可交付（Linux + 桌面 + 触摸）2–6 周。**

## 2. 你的 IPSW 解剖结果（实测，不是推测）

文件：`~/Downloads/iPhone10,3,iPhone10,6_16.5_20F66_Restore.ipsw`（6,165,698,198 字节，91 个条目；**下载目录里有两份完全相同的 6.1 GB 副本，共 12 GB，可以删一份**）

| 组件 | IM4P 类型 | 描述 | 载荷 | KBAG | 结论 |
|---|---|---|---|---|---|
| iBoot.d22 | `ibot` | iBoot-8422.120.66 | 1,110,800 | **有** | **加密**，无 GID 不可解 |
| LLB.d22 | `illb` | iBoot-8422.120.66 | 1,110,800 | **有** | **加密** |
| sep-firmware.d22 | `sepi` | (哈希串) | 1,405,840 | **有** | **加密**，且需要 SEP 硬件 |
| DeviceTree.d22ap | `dtre` | EmbeddedDeviceTrees-7153.122.1 | 33,632 → **LZFSE** → 186,040 | 无 | Apple 私有 DT 格式 |
| kernelcache.release.iphone10b | `krnl` | KernelCacheBuilder_release-2429.120.2 | 18,183,321 → **LZFSE** → **50,888,732** | 无 | 可解，见下 |

kernelcache 解压后结构：`0xCAFEBABE` fat 头（1 个 arch，cputype `0x0100000C` = arm64）→ `MH_EXECUTE`，25 条 load command，**962 个 kext bundle id**。
关键实测：
- 962 个 kext 里，`mediatek` / `mt6833` / `qualcomm` / `exynos` / `snapdragon` 出现次数 = **0**。
- 平台相关：`AppleARMPE`（平台专家，编在内核里）、`AppleSEPManager`、`AppleSEPKeyStore`、`AppleAOP`、`AppleSPMI`、`AppleM68`、`AppleSamsungSerial`、`AppleMultitouchSPI`、`AppleHapticsSupportCallan`、`AppleAcornDisplayPMU`。
- 图形：**`com.apple.AGXG10P`**（A11 的 GPU 驱动，闭源）+ `AGXFirmwareKextRTBuddy`。没有 Mali。
- DeviceTree 里：`arm-io,t8015`、`aic,1`、`pmgr1,t8015`、`DISP0_FE/BE/GP`、`SEP_EISP`、`ANS2`、`AOP_CPU`、`SMC_CPU` —— 整棵树都是 Apple 硬件。

> 注：网上有说法称 iPhone10b 的 kernelcache 是 LZSS（blacktop/ipsw #1324）。**本机实测是 LZFSE**：载荷前 4 字节 `62 76 78 32`（"bvx2"），用 macOS libcompression 的 `COMPRESSION_LZFSE (0x801)` 一次解出 50,888,732 字节。以实测为准。

## 3. 可行性判定：逐层

| 层 | 判定 | 判据 | 代价 |
|---|---|---|---|
| **L1 引导** | **不能用 Apple 的，自写 loader** | iBoot 加密 + 写死 Apple 外设地址 | 写一个裸机 loader（参考 hakios `mtkloader/`） |
| **L2 内核** | **可行，重写平台层** | XNU 开源；`AppleARMPE/AppleARMIO` 是闭源 kext，必须自写 GenericARMPE；GICv3 + PSCI + 13 MHz timer + 16K 页 | 2–4 人月 |
| **L3 用户态** | **原样可跑** | 用户态不需要 Apple 硬件；launchd→backboardd→SpringBoard 只需要 IOKit 服务族存在 | 0（镜像已有） |
| **L4 存储** | **必须新写** | HakiOS 只有 eMMC/MSDC0 驱动（`hakios.mtk_emmc.c`），**你是 UFS**，MTK UFS 控制器和 Qualcomm 完全不同 | 1–2 人月（最大单点） |
| **L5 显示** | **最容易** | 直接用 LK 留下的 framebuffer 0x76720000 | 1–2 周 |
| **L6 输入** | **中等** | 触摸 = SPI4 + ILITEK 协议；按键 = KPD 寄存器 + PMIC | 3–6 周 |
| **L7 图形加速** | **可选，代价大** | CPU 软渲染 20–30 fps（ios-sweet 路线）；Mali-G57 需要自写 Metal（HakiOS MT6768 已在 Mali-G52 上做过） | 6–12 人月 |
| **L8 SEP / 安全** | **永久损失** | Keychain/Data Protection/Face ID/attestation/App Store 全废；AMFI/Sandbox 关闭 | 不可逆 |

**一句话**：CPU 指令集不是墙（ARMv8 通用），墙是 **SEP、iBoot 信任链、Apple 闭源平台 kext、以及 UFS 驱动**。

## 5. 移植方案（M0 → M7）

> 顺序不是随便排的：**先用 Linux 把硬件摸清楚，再让 XNU 用上这些知识**。
> 理由：Linux 侧有现成的同 SoC 移植可抄、有 UART 日志、有 panic 信息；XNU 侧什么都没有，黑盒调试成本高一个数量级。

### M0 基线与安全 —— 已完成
- [x] 36 个分区备份（817 MB）+ MD5
- [x] 活动设备树导出、boot/dtbo 解包
- [x] fastboot 能力探测（结论：只能 flash，不能 boot）
- [x] IPSW 解剖
- [x] xnusys 现状确认（已有 iOS 16.5 APFS 镜像）
- 完成判据：任意时刻能 `fastboot flash boot assets/device/backup/boot.img` 回到原厂

### M1 Linux bring-up（2–6 周）★ 先做这个
**目标**：这台机器上出现 Linux 画面，触摸能点。

1. 拉厂商源码（4.14.186，branch `oppo/mt6833_s_12.1_oppo_k10_5g`）

        git clone -b oppo/mt6833_s_12.1_oppo_k10_5g https://github.com/oppo-source/android_kernel_oppo_mt6833 vendor-kernel
        cd vendor-kernel && make ARCH=arm64 k6833v1_64_defconfig

2. 改 config：`CONFIG_DRM_SIMPLEDRM=y` / `CONFIG_SYSFB_SIMPLEFB=y` / `CONFIG_FB_SIMPLE=y` / `CONFIG_BLK_DEV_INITRD=y` / `CONFIG_RD_GZIP=y`；**`CONFIG_FRAMEBUFFER_CONSOLE` 必须 =n**（MT6833 上开 fbcon 会 bootloop）；去掉所有 `-Werror`
3. 在 DTS 的 `chosen` 里加 simple-framebuffer（**不要自己写 reserved-memory，LK 会插 mblock-* 节点**）
4. 改 `drivers/of/of_reserved_mem.c`：把 `compatible = "mediatek,framebuffer"` 的区块强制当 `no-map`（LK 不写 no-map，内核会把它当 RAM，`ioremap_wc` 拒绝映射）
5. 打 header v2 boot.img（见 `scripts/mkboot-mt6833.sh`）
6. `fastboot flash boot boot-mainline.img` → 重启 → 看画面
7. 飞 UART（GPIO61/62，921600 8N1）拿 `earlycon=mt6833uart,0x11002000` 日志

- 完成判据：屏幕出现 Linux 控制台/Phosh，`/dev/input/event*` 有触摸事件

**这一步同时产出 XNU 需要的全部硬件参数**：DSI 时序、触摸 SPI 协议、KPD 寄存器行为、PMIC 电压轨、UFS 初始化序列。

### M2 XNU 引导链（1–2 月）
**目标**：XNU banner 打出来。

1. 拿 hakios `mtk/loader/` 当骨架：裸机 arm64，关 MMU，通过存储控制器读数据，构造 XNU 的 ADT 和 boot-args
2. 链接地址 **0x40080000**（LK 的 `kernel_addr`），入口按 arm64 Image 协议
3. 平台层：GICv3（MT6833 用 GICv3，和 SM7150 同代，ios-sweet 的代码可直接参考）、PSCI CPU_ON、13 MHz arch timer、**16 KB 页**（A55/A76 都支持）
4. 用 `fastboot flash boot` 装 loader（**不能 `fastboot boot`**）
- 完成判据：UART 或 framebuffer 上出现 XNU 版本串

### M3 存储（1–2 月）★ 最大单点
**目标**：挂上 xnusys 里的 APFS 卷。

- MTK UFS 主机驱动（`11270000.ufshci`）：HakiOS 只有 eMMC/MSDC0 驱动（`hakios.mtk_emmc.c`），**UFS 要新写**。可参考 Linux 的 `drivers/ufs/host/ufs-mediatek.c`
- APFS 只读（ios-sweet 用 HFS+，HakiOS 用 APFS；你盘上是 APFS，走 HakiOS 路线）
- 或者退一步：**把 iOS 根改写成 HFS+ 放进 userdata**（ios-sweet 路线，工具链更成熟），代价是要重做一次镜像
- 完成判据：能读出 `/System/Library/CoreServices/SystemVersion.plist`

### M4 iOS 用户态（1–2 月）
**目标**：launchd → backboardd → SpringBoard 起来。

- 你的 xnusys 里已经有 iOS 16.5 的 System 卷（2.46 GiB 已用，`mkapfs.py (darwin-redwood)` 生成）
- 需要补的 IOKit 服务：`IOHIDFamily`、`AppleKeyStore`（桩）、`IOSurface` + `IOMobileFramebuffer`、`IOMedia`
- boot-args 参考：`cpus=6 keepsyms=1 rd=... rootrw=1 launchd_unsecure_cache=1 wdt=-1`
- 完成判据：SpringBoard 进程活着（哪怕黑屏）

### M5 显示与输入（3–6 周）
- 显示：把帧写进 **0x76720000**（1088×2400，stride 4352，a8r8g8b8），iOS 侧按 iPhone X 的 1125×2436 缩放
- 触摸：SPI4（0x11018000，CS0，9.6 MHz）+ ILITEK ILI7807S 协议 → HID digitizer 事件；注意 UIKit 靠 EventMask 0xb0007 的 bit 0x800/0x1000/0x2000 判定"从边缘开始"，不设的话上滑回桌面手势失效（ios-sweet 0071 的教训）
- 按键：KPD 寄存器轮询（音量上 GPIO1 / 音量下 GPIO80）+ MT6359 pwrkey
- 完成判据：**锁屏出现，能上滑解锁，能点开设置**

### M6 桌面（达标点）
- 完成判据（用户定义的目标）：**进入桌面 / 显示正常 / 按键可用 / 触摸可用**

### M7（可选）GPU
- Mali-G57 MC2 + panfrost + 自写 Metal（抄 hakios-mt6768 的 `hakios.mali.c/cpp` 和 `hakios-metal`）
- 代价：6–12 人月；收益：帧率从 20–30 提到 100+

## 6. 这台机器特有的坑（每条都有出处）

1. **`fastboot boot` 会崩 LK**（我实测）。所有刷写只能走 `fastboot flash boot`，`boot` 分区 32 MiB 是硬上限。
2. **framebuffer 的 reserved-memory 没有 `no-map`**。内核会把它当可用 RAM，`ioremap_wc` 会拒绝映射。必须在 `of_reserved_mem.c` 里对 `mediatek,framebuffer` 强制 no-map。
3. **不要自己写 reserved-memory**。LK 启动时会往 DTS 里插 `mblock-N-*` 节点（你这台有 30 个），冲突会走 `reserved_memory_conflict_check` 直接挂死。
4. **fbcon 在 MT6833 上会 bootloop**（thunder-os 实测）。用 simpledrm + DRM 用户态。
5. **UFS 写保护**：MTK bootloader 会给 boot 分区开 power-on write protection，Linux 侧写 boot 会 DATA PROTECT（sense key 0x7）→ 内核更新只能走 fastboot，重启后才解。
6. **PMIC 电量算法**：MT6359 的 gauge 在 Android 是守护进程算的。没有它 `capacity` 读 -1，UPower 当 0% → critical-battery 直接 PowerOff（8–60 秒内）。**必须在核内跑算法或禁用 critical 链。**
7. **硬件看门狗**：preloader/ATF 装了 WDT，用户态不 kick 几秒就复位。调试期加 `initcall_blacklist=mtk_wdt_driver_init`，正式跑要有 kick 线程。
8. **AVB / dm-verity**：刷了自定义 boot，Android 起不来是正常的（`vbmeta` 校验失败）。回滚 = 刷回 `assets/device/backup/boot.img`。
9. **LK 会按节点名找 stock 节点并叠 dtbo**（`dtbo_idx=9`）。DTB 必须保留 stock 节点骨架（可以 `status = "disabled"`），否则 LK 拒绝启动。参考 a22x 的 `gen-lk-compat-dtsi.py`。
10. **触摸是 ILITEK ILI7807S，不是网上常见的 Novatek**。TDDI 意味着显示和触摸同一颗芯片，面板初始化时序会影响触摸复位。
11. **`vendor_boot` 分区全 0**，LK 不读它。所有 DTB 走 boot.img 的 header v2 dtb 段（Android DT table 格式）。
12. **两个 6.1 GB 的 IPSW 副本**占 12 GB，删一份。而且版本是 **16.5 (20F66)**，ios-sweet 的工具链锚定 **16.7.16 (20H392)**，HakiOS 用的是 **16.5** —— 你的 ipsw 版本对 HakiOS 路线是对的，对 ios-sweet 路线要换。
